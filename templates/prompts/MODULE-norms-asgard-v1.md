# МОДУЛЬ НОРМ «АСГАРД» (общий) — v1

> **Что это.** Единый источник истины по расчётной механике для обеих систем просчёта
> ООО «Асгард-Сервис»: быстрого просчёта одним агентом (`PROMPT-quick-v4.md`) и
> кондуктора с агентами (`PROMPT-conductor-v2.md`). Один и тот же текст подставляется
> сервером в оба промпта на этапе сборки (плейсхолдер `{{NORMS_MODULE}}`), а для
> агентов-калькуляторов «без LLM» (`call_labor_calculator`, `call_resource_planner`,
> `call_crew_composer`, `call_site_conditions`) служит ТЕХНИЧЕСКИМ ЗАДАНИЕМ, которое
> они реализуют в коде.
>
> **Зачем общий модуль.** Чтобы быстрый просчёт и кондуктор считали трудозатраты,
> бригаду, ОТ/ПБ-надбавки и цены по ОДНИМ правилам. Любое изменение нормы правится
> здесь — в одном месте.
>
> **Главная цель модуля — ДЕТЕРМИНИЗМ.** Один и тот же вход обязан давать один и тот
> же `work_days` и `crew_count`. Это достигается тремя приёмами: (1) из любого
> диапазона всегда берётся ОДНО значение «по умолчанию»; (2) люди и смены всегда
> округляются ВВЕРХ; (3) порядок позиций и формулы зафиксированы. Если три прогона
> на один вход дают разные числа — нарушено одно из этих правил.
>
> Версия v1 — 19.06.2026. Совместим с Claude Opus 4.8, GPT-5.5, Gemini 3.5.

## 0. ЖЕЛЕЗНЫЕ ПРАВИЛА ДЕТЕРМИНИЗМА (читать первым)

1. **Никогда не выбирай число «на глаз» и не бери середину диапазона.** Для любой нормы,
   производительности, цены-заглушки и коэффициента бери СТРОГО колонку/значение
   «по умолчанию», указанное в этом модуле.
2. **Округление — всегда вверх (`⌈ ⌉`, ceil):** число людей, число смен, `work_days`,
   `road_days`. Деньги — до целого рубля. Промежуточные человеко-часы — 2 знака.
3. **Порядок вычислений фиксирован** (раздел 6). Не меняй последовательность шагов.
4. **Сортировка позиций фиксирована:** работы — по типу (в порядке перечисления
   `work_type` в разделе 1), внутри типа — по диаметру/Ду по возрастанию.
5. **Считай ПОЛНЫЙ объём.** «2 аппарата по 1 718 труб» = 3 436 труб. Всегда умножай
   на число единиц оборудования.
6. **Не выдумывай данные.** Наличие/марку/цену оборудования бери из БД склада или
   веб-поиска (раздел 8). Норму, которой нет в РФ как госнорматива, помечай
   `basis: "expert_estimate"`. Любое допущение фиксируй явно.
7. **Каждый промежуточный результат фиксируй в трассе расчёта** (`calc_trace` в JSON
   быстрого просчёта; артефакт `labor_calc` у агента кондуктора). Незаписанный
   промежуточный шаг — источник разброса.

## 1. ГЛОССАРИЙ И ЕДИНИЦЫ

Используй термины единообразно. Не путай человеко-часы, человеко-смены и календарные дни.

- **`man_hours` (чел-ч)** — абсолютная трудоёмкость в человеко-часах. Не зависит от длины смены.
- **`shift_hours` / `t_см`** — длительность одной смены, ч. Значения:
  - **24/7 (дефолт компании)** → `t_см = 12`, число смен в сутки **`n = 2`** (день+ночь).
  - односменный режим → `t_см = 11` (вахта) или `t_см = 8` (обычный день), `n = 1`.
- **`person_shifts` / `T_см`** — потребные человеко-смены на весь объём (в сменах по `t_см`).
- **`k_irv`** — коэффициент использования рабочего времени (ПЗР, обед, переходы,
  инструктажи). Фикс. **`k_irv = 0.82`**.
- **`window_days`** — окно работ = `{{N}}` КАЛЕНДАРНЫХ дней (`{{start_date}}`→`{{end_date}}`).
  Жёсткая верхняя граница пребывания бригады (раздел 7).
- **`road_days`** — дни в пути бригады В ОДНУ СТОРОНУ (люди, поезд/самолёт). Туда и обратно = `road_days × 2`.
- **`mobdemob_days`** — мобилизация + демобилизация на объекте. По умолчанию **4** (2+2).
- **`W_avail`** — доступные календарные дни под чистую работу на объекте
  `= window_days − road_days×2 − mobdemob_days`.
- **`work_days`** — чистые рабочие смены, ВЫЧИСЛЯЕМЫЕ из объёма (раздел 6). НЕ «окно минус накладные».
- **`total_days`** — фактическая длительность выезда `= work_days + road_days×2 + mobdemob_days`.
  Может быть МЕНЬШЕ окна (бригада возвращается, выполнив объём) — это экономит командировочные.
  Всегда `≤ window_days`.
- **`crew_count`** — итоговая численность, всего человек (исполнители + наблюдающие +
  спасатели + мастера + ИТР).
- **`N_exec_per_shift`** — число исполнителей в ОДНОЙ смене (без наблюдающих/мастера/ИТР).
- **Балл** = 500 ₽. День дороги = 6 баллов = **3 000 ₽/чел/день** (фикс.).
- **Ставка ИТР (РП)** = **10 000 ₽/день** (фикс., НЕ из тарифной сетки).
- **Категории объекта / корзины тарифа:** `MLSP` (морские платформы), `LAND` (обычные
  наземные), `LAND_HEAVY` (тяжёлые наземные), `WAREHOUSE` (склад).
- **Типы работ (`work_type`):** `HYDRO_MECH` / `HYDRO_DYN` (гидромех./гидродин. очистка),
  `CHEM` (химпромывка/травление/пассивация), `HVAC` (инженерные системы ИТП/ЦТП),
  `MOUNT` (монтаж/демонтаж/такелаж/сварка), `INSULATION` (теплоизоляция).

циркуляции — **8 ч на контур** (`basis:"expert_estimate"`), персонал обвязки/контроля
**3 чел/смену** (фикс.), не масштабируется объёмом. Несколько контуров — последовательно
или параллельно по числу насосных постов.

**Технический ориентир ГДО** (для здравого смысла, не для замены норм): установки
сверхвысокого давления 500–3000 бар, 15–250 л/мин; чистка одним копьём ≈ 1 п.м/6 с
«чистого» хода.

## 5. ОБЯЗАТЕЛЬНЫЙ ПЕРСОНАЛ ОТ/ПБ (детерминированные правила R1–R8)

Это НЕ оценка, а жёсткие «ЕСЛИ → ОБЯЗАТЕЛЬНО +N роли Z». Применяются к составу смены
ПОСЛЕ расчёта числа исполнителей (раздел 6). В режиме 24/7 — в КАЖДОЙ смене.

| № | ЕСЛИ условие | ОБЯЗАТЕЛЬНО добавить | Основание |
|---|---|---|---|
| R1 | Работа внутри ёмкости/аппарата/колодца (ОЗП ёмкостного сооружения) | **+1 наблюдающий + 1 спасатель снаружи** (бригада ≥3, двое снаружи) | 902н п.199 |
| R2 | ОЗП проходного коллектора | **+1 наблюдающий + 2 спасателя снаружи** | 902н п.198 |
| R3 | Несколько люков/постов входа одновременно | наблюдающий — отдельный на КАЖДЫЙ люк; спасательное звено может обслуживать пост | 902н п.56, п.199 |
| R4 | Газоопасные работы внутри ёмкости | **+1 ответственный за проведение газоопасных работ** (бригада ≥2: работающий+наблюдающий) | ФНП 528 |
| R5 | Огневые работы (сварка/резка) | **+1 наблюдающий за огневыми работами** + контроль воздушной среды | ФНП 528 |
| R6 | Работы на высоте по наряду-допуску | **+1 ответственный руководитель работ** (гр.3, из ИТР) — ОДИН на объект, не на бригаду | 782н |
| R7 | Совмещение «ОЗП + спуск (высота)» | наблюдающий/спасатели должны иметь группу по высоте; численность сверх R1 не растёт, но удорожание по допускам | 902н+782н |
| R8 | МЛСП, огневые работы | состав поста по СТО оператора + наблюдающий за огневыми; весь персонал с BOSIET | ФНП 528 + СТО |

**Правила совмещения ролей (фикс.):**
- Наблюдающий — самостоятельная роль, НЕ совмещается с работой внутри; находится у люка
  весь период работ.
- Мастер НЕ считается наблюдающим (он руководит).
- По 902н п.199 функции наблюдающего и спасателя могут совмещаться. Детерминированная
  модель для безопасности берёт МИНИМУМ по букве: **+2 снаружи** (наблюдающий + спасатель)
  на пост ОЗП. Совмещение в одного — только если ППР/наряд это прямо разрешает (ручная
  правка с флагом).
- R6 (ответственный руководитель, высота) — ОДИН на объект, закрывает все бригады; считать +1 на проект.

## 6. ДЕТЕРМИНИРОВАННЫЙ АЛГОРИТМ: ОБЪЁМ → ТРУДОЁМКОСТЬ → БРИГАДА И `work_days`

Строгая последовательность. Один вход → один выход.

**Шаг 1. Разложить объём** на однородные позиции (вид работ × диаметр/тип × число единиц).
Фиксированная сортировка (раздел 0, п.4). Полный объём (раздел 0, п.5).

**Шаг 2. Базовая трудоёмкость `T₀` (man_hours).** По каждой позиции:
- ЕНиР (тип А): `man_hours = qty × Н.вр` (таблицы 3.1–3.2, поправки Е26/Е11).
- Экспертные (тип Б): `man_hours = qty / производительность_на_смену × 12` (таблица 3.5).
- Химпромывка: `man_hours = число_контуров × 8` (длительность цикла); персонал — фикс. 3 чел/смену.
- `T₀ = Σ man_hours` по всем позициям.

**Шаг 3. Коэффициенты.** `T = Σ(man_hours_i × Π k_j)` (раздел 4; без двойного учёта отложений).

**Шаг 4. Реальные потери.** `T_factual = T / k_irv = T / 0.82`.

**Шаг 5. Перевод в смены.** Определи режим: **24/7 (дефолт) → t_см=12, n=2**; односменный
(только при явном запрете ночных, см. промпт) → t_см=8 или 11, n=1.
`T_см = T_factual / t_см`. Округление вверх до 0.1.

**Шаг 6. Доступное окно.**
```
road_days  — по таблице 7 (детерминированно).
mobdemob_days = 4 (если ТЗ не диктует иное).
W_avail = window_days − road_days×2 − mobdemob_days.
```
Если `window_days` не задан — `W_avail` не ограничивает (бери из объёма), но это редкий случай.

**Шаг 7. Минимальные исполнители в смене (используем окно полностью → минимальная бригада).**
```
N_exec_per_shift = ⌈ T_см / (n × W_avail) ⌉
```
Это наименьшее число исполнителей в смене, при котором объём укладывается в окно при `n` сменах.

**Шаг 8. Ограничение по фронту работ.** `N_front_max` = число одновременных рабочих мест ×
человек на место (например, 2 теплообменника = 2 поста ГДО). Если `N_exec_per_shift >
N_front_max` и добавить фронты нельзя → `schedule_conflict = true` (раздел приоритетов
ниже). Если можно добавить фронты — увеличь `N_front_max`. Практический минимум:
`N_exec_per_shift ≥ 1` (для ОЗП — ≥1 исполнитель, к нему пристёгиваются наблюдающие R1).

**Шаг 9. `work_days` (обратный расчёт).**
```
work_days = ⌈ T_см / (N_exec_per_shift × n) ⌉
```
По построению `work_days ≤ W_avail`. Если из-за округления `work_days > W_avail` —
увеличь `N_exec_per_shift` на 1 и повтори шаг 9.

**Шаг 10. Состав смены и итоговая численность.** Собери ОДНУ смену:
```
смена = N_exec_per_shift исполнителей
      + наблюдающие/спасатели по R1–R5 (на каждый пост ОЗП +2 снаружи; огневые +1)
      + 1 мастер
```
Итог:
```
crew_count = смена × n            (для 24/7 — две сменные бригады)
           + 1 ИТР (РП)           (на весь проект)
           + ответственный руководитель по R6 (если высота по наряду; +1 на проект)
```

**Шаг 11. `total_days`.** `total_days = work_days + road_days×2 + mobdemob_days`. Проверь
`total_days ≤ window_days`. Командировочные (пайковые, проживание, ИТР) считаются ×
`total_days` (а не × окно): если объём сделан раньше — бригада возвращается, экономя расходы.

**Шаг 12. Самопроверка (раздел 9).** Если не сходится — пересчёт.

**ПРИОРИТЕТ ПРИ КОНФЛИКТЕ ОГРАНИЧЕНИЙ:** (1) безопасность (персонал ОТ/ПБ R1–R8 урезать
нельзя); (2) срок (`total_days ≤ window_days`); (3) фронт. Если безопасность и срок
несовместимы с фронтом → `schedule_conflict = true`, рекомендация
`"extend_window_or_split_shifts"`. НИКОГДА не выводи «в окно не помещается» молча —
только через флаг с числами.

## 7. РАСЧЁТ `road_days` И МАРШРУТ (детерминированно)

База выезда — **Саратов**. Маршрут полевых: **Саратов → Москва (склад, 2–3 дня:
комплектация, погрузка, СИЗ, инструктаж) → город объекта**, обратно так же. Авиарейсов
из Саратова почти нет → Саратов↔Москва ВСЕГДА поезд.

**Таблица `road_days` (в одну сторону, люди), по удалённости объекта от Москвы:**

| Условие | road_days (одна сторона) |
|---|---|
| объект ≤ 800 км от Москвы (поезд) | 1 |
| 800–2500 км (поезд) | 2 |
| > 2500 км, но есть аэропорт (самолёт) | 2 |
| > 2500 км, только поезд | 3 |

В окно входит дорога ТУДА и ОБРАТНО (`road_days × 2`). **Техника едет отдельно/заранее —
её время в пути в `road_days` бригады НЕ входит** (учитывается в логистике, раздел 8).

## 8. ПРОТОКОЛ ВЕБ-ПОИСКА ЦЕН (кросс-модельный) + ЗАГЛУШКИ

> **Принцип: цены из памяти модели ЗАПРЕЩЕНЫ — они устаревшие.** Для каждой ценовой
> позиции модель ОБЯЗАНА выполнить веб-поиск (`web_search`). Работает одинаково в
> Claude (web_search/web_fetch), GPT (browsing/tool calling), Gemini (Grounding). В
> кондукторе этим занимаются агенты `call_market_search`, `call_travel_pricer`,
> `call_procurement_analyzer`, `call_permits_planner`.

**Алгоритм по каждой ценовой позиции:**
1. Определи, нужна ли актуальная цена (позиция есть в перечне 8.2 → да).
2. Сформируй запрос по шаблону из 8.2 (рус., ≤6 слов, + «цена»/«аренда сутки» + 2025/2026).
3. Выполни `web_search`; при наличии релевантного результата открой источник и извлеки число.
4. Зафиксируй: `value`, `currency:"RUB"`, `source_url`, `source_name`, `price_date`, `unit`.
5. Несколько цен → МЕДИАНА из 3+ источников; при 2 источниках — больший (консервативно);
   при разбросе > 40 % → флаг `price_variance_high:true` и верхняя граница.
6. **Поиск недоступен ИЛИ 0 результатов → бери ВЕРХНЮЮ границу заглушки (8.2),
   ставь `needs_manual_price:true`, `price_source:"stub_upper"`.**
7. **Никогда не бери цену из памяти.** Если `price_source:"web"`, а `source_url` пуст —
   ответ невалиден, переделай.

**Анти-лень (структурное принуждение):** по каждой ценовой строке требуются поля
`price_source` ∈ {"web","stub_upper"} и `source_url`. Пустой URL при `"web"` = брак.

## 9. САМОПРОВЕРКА ПЕРЕД ВЫДАЧЕЙ (жёсткий шлюз)

1. **Детерминизм:** все нормы/коэффициенты/цены-заглушки взяты по «умолчанию», не из середины диапазона.
2. **Дни:** `total_days = work_days + road_days×2 + mobdemob_days ≤ window_days`.
3. **`work_days` вычислен** по разделу 6 (формула `⌈T_см/(N×n)⌉`), не «окно минус накладные».
4. **Бригада:** исполнители по объёму; ОЗП → +наблюдающий+спасатель на пост; огневые → +наблюдающий;
   высота по наряду → +ответственный руководитель; 24/7 → две смены; ровно 1 ИТР.
5. **Округление вверх** для людей и смен; деньги — целые рубли.
6. **Арифметика:** `personnel total = count × rate × days`; `travel total = count × price`;
   итоги по блокам и общая сумма пересчитаны и совпадают (расхождение из-за округлений ≤ 5 %).
7. **ИТР:** 10 000 × `total_days`, НЕ продублирован в строке «дни дороги».
8. **Оборудование** учтено в `current_costs` (амортизация по `unit_value_rub`) ИЛИ в `purchases_needed`;
   наличие — из БД склада, цены — из веб-поиска или заглушки-ВЕРХ; марки не выдуманы.
9. **Цены:** у каждой ценовой строки есть `price_source` и (если `web`) `source_url`+`price_date`.
10. **Флаги** выставлены: `schedule_conflict`, `needs_manual_price`, `price_variance_high`,
    `basis:"expert_estimate"` на экспертных нормах.

Любой невыполненный пункт → пересчёт, не выдавай результат.

## 10. ДВА ЭТАЛОННЫХ ПРИМЕРА (сквозной расчёт по разделу 6)

### Пример A — лёгкая смета: изоляция 240 м² Ø159, полимер, высота с лесов
**Вход:** 240 м², Ø159, Е11-3 полимер = 0.23 man_hours/м²; высота с лесов (k=1.10); окно 14 кал.
дней; объект 700 км от Москвы; не ОЗП, без огневых. Режим — по умолчанию 24/7.
- Шаг 2: `T₀ = 240 × 0.23 = 55.2` man_hours.
- Шаг 3: `T = 55.2 × 1.10 = 60.7`.
- Шаг 4: `T_factual = 60.7 / 0.82 = 74.0`.
- Шаг 5: 24/7 → t_см=12, n=2; `T_см = 74.0 / 12 = 6.2` смен.
- Шаг 6: road=1 (≤800 км); mobdemob=4; `W_avail = 14 − 2 − 4 = 8`.
- Шаг 7: `N_exec = ⌈6.2 / (2×8)⌉ = ⌈0.39⌉ = 1`. Изоляция выполняется звеном 2 чел → практический минимум исполнителей в смене = 2.
- Шаг 9: `work_days = ⌈6.2 / (2×2)⌉ = ⌈1.55⌉ = 2`. (≤ 8 ✓)
- Шаг 10: смена = 2 исполнителя + 1 мастер = 3; 24/7 → ×2 = 6; +1 ИТР; высота с лесов (не по наряду на высоте 1.8 м — R6 не триггерится автоматически, но если наряд-допуск на высоту требуется — +1). Без наряда на высоту: `crew_count = 6 + 1 = 7`.
- Шаг 11: `total_days = 2 + 2 + 4 = 8 ≤ 14 ✓`. (Бригада возвращается, не «досиживает» окно — экономия пайковых/проживания.)
- Самопроверка: дни ✓, арифметика ✓. **Итог: crew_count = 7, work_days = 2, total_days = 8.**

### Пример B — ОЗП 24/7: химико-механическая очистка 2 ёмкостей + пучки, накипь
**Вход:** 2 ёмкости (ОЗП) + трубные пучки 2×800 = 1600 трубок, отложения «накипь»; объект
химзавод Кемерово (~3500 км от Москвы, есть аэропорт); окно 30 кал. дней; у всех ОТЗП.
Режим 24/7 (дефолт). Фронт: 2 поста ГДО (по 2 чел.) + работы в 2 ёмкостях.
- Шаг 2: пучки `1600 / 95 × 12 = 202.1` man_hours; ёмкости (химико-мех. внутри ОЗП) —
  допустим очистка стенок 2 ёмкостей экспертно ~2 смены исп. каждая = `4 × 12 = 48` man_hours.
  `T₀ = 202.1 + 48 = 250.1`.
- Шаг 3: ОЗП (k=1.25), СИЗОД при газоопасной среде (k=1.30 — если применимо; примем ОЗП без СИЗОД): `T = 250.1 × 1.25 = 312.6`.
- Шаг 4: `T_factual = 312.6 / 0.82 = 381.2`.
- Шаг 5: 24/7 → `T_см = 381.2 / 12 = 31.8` смен.
- Шаг 6: самолёт (>2500 км, аэропорт) → road=2; mobdemob=4; `W_avail = 30 − 4 − 4 = 22`.
- Шаг 7: `N_exec = ⌈31.8 / (2×22)⌉ = ⌈0.72⌉ = 1`. Но фронт допускает до 2 постов × 2 = 4 исполнителя; берём практический минимум по объёму = 1, проверяем срок.
- Шаг 9: при `N_exec=1`: `work_days = ⌈31.8 / (1×2)⌉ = 16 ≤ 22 ✓`. (Можно 1 исполнителя/смену, но для ОЗП+двух фронтов реалистично 3 — это управленческое решение; детерминированный минимум по сроку = 1, но crew_rules для ОЗП с двумя ёмкостями диктуют ≥ число постов. Берём `N_exec = 3` как практический минимум по фронту/режиму.) При `N_exec=3`: `work_days = ⌈31.8 / (3×2)⌉ = ⌈5.3⌉ = 6 ≤ 22 ✓`.
- Шаг 10: смена = 3 исполнителя + (ОЗП R1: на каждый из ≤3 постов +1 наблюдающий +1 спасатель; при едином спасательном звене — 3 наблюдающих + 1 спасатель) + 1 мастер. Возьмём по букве 1:1: 3 исполнителя + 3 наблюдающих + 1 мастер = 7; 24/7 → ×2 = 14; +1 ИТР = **15**.
- Шаг 11: `total_days = 6 + 4 + 4 = 14 ≤ 30 ✓`.
- Самопроверка: ОЗП-персонал добавлен ✓, 24/7 две смены ✓, ИТР один ✓, дни ✓.
  **Итог: crew_count = 15, work_days = 6, total_days = 14.**

> Примечание к примеру B: видно, как объём (1600 трубок) даёт `work_days = 6`, а не «22
> по окну». Бригада возвращается на 16-й день — это честнее и стабильнее, чем «досиживать»
> окно. Если заказчик оплачивает простой/присутствие — это отдельная строка, не work_days.

## 11. ОГОВОРКИ (Caveats)
- ЕНиР формально не действует с 01.01.2021 (регуляторная гильотина) — используется как
  технический ориентир трудоёмкости, не как основание сметной стоимости (для неё — ГЭСН/ФЕР 2026).
- Экспертные производительности (раздел 3.5) — допущения (`expert_estimate`), госнорм нет.
  Калибровать по факту бригад Асгарда; заменить на внутренние нормы после 10–15 объектов.
- Цены-заглушки (8.2) намеренно ВЕРХНИЕ (консервативно) и должны замещаться веб-поиском.
