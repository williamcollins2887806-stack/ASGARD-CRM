# TING-CAPACITY — замеры вместимости комнаты

Дата создания: 2026-11-05
Статус: **шаблон + методика**. Числа заполняются на целевом сервере; без них волна 2 не начинается.

## Почему этот файл обязателен

Прошлый план обещал «40 участников с видео» и «stretch 100». Аудит показал, что это невозможно
на одной ноде. Официальный бенчмарк LiveKit (150 издателей × 150 подписчиков) — это **16 ядер
и ~744 Мбит/с исходящего**. Комната целиком живёт на одной ноде: кластер добавляет **комнаты**,
а не размер комнаты.

Поэтому вместимость считается по формуле, а не по числу людей:

```
исходящий трафик ≈ (издатели × подписчики) × битрейт
```

Для 8 человек с камерой 720p (~1,5 Мбит/с): 8 × 7 × 1,5 ≈ **84 Мбит/с** на комнату.

## Целевые режимы волны 1

| Режим | Ожидание | Как проверяем |
|-------|----------|---------------|
| 2 участника, оба с камерой | стабильно, первый кадр < 2 с | медиа-smoke |
| 5 участников, все с камерой | стабильно, без freeze | медиа-smoke |
| 8 участников, все с камерой | стабильно | медиа-smoke |
| 12 участников, все с камерой | верхняя граница, допустимы краткие просадки | медиа-smoke |
| 25 участников, 3–6 видео | стабильно в audio+video-слотах | load-прогон |
| 40 участников, 3–6 видео | стабильно, честный UI «видео-слоты заняты» | load-прогон |

Всё, что выше 12 с камерой, — **не обещаем** в волне 1. `max_video` реально применяется:
когда слоты заняты, новый участник входит audio-only (`canPublishSources: ['microphone']`).

## Методика замера

### 1. SFU-нагрузка (синтетика)

```bash
# на сервере, где стоит livekit
livekit-cli load-test \
  --url ws://127.0.0.1:7880 \
  --api-key "$LIVEKIT_API_KEY" \
  --api-secret "$LIVEKIT_API_SECRET" \
  --room ting-load \
  --publishers 8 --subscribers 8 --duration 120s --video-resolution 720p
```

Смотреть: `CPU`, `outgoing bytes/s`, `packet loss`, `freeze count` в выводе и `docker stats`.

### 2. Продуктовый прогон (реальные комнаты)

```bash
# на клоне
BASE_URL=http://127.0.0.1:3100 LOGIN=<admin> PASSWORD=<pass> \
  node tests/ting/load/room_load.js --participants 12 --duration 120
```

Скрипт создаёт комнату, выдаёт N токенов, подключает headless-клиентов LiveKit и пишет
`tests/reports/TING-LOAD-<N>.json`: время до первого кадра, freeze rate, reconnect count, CPU.

### 3. NAT-матрица (обязательно вне сервера)

| Сеть | Ожидание |
|------|----------|
| Офис ASGARD (корп. NAT) | вход < 3 с, без relay или через relay |
| Домашний Wi-Fi | вход < 2 с |
| LTE (мобильный) | вход < 4 с, relay допустим |
| Wi-Fi телевизора в зале | вход < 4 с, стабильное видео |

Для каждого — зафиксировать `candidate.type`: `host`/`srflx`/`relay` и долю relay-сессий.

## Форма отчёта (заполняется после прогона)

```json
{
  "date": "YYYY-MM-DD",
  "server": { "cpu_cores": 0, "ram_gb": 0, "nic_mbps": 0 },
  "runs": [
    { "participants": 8, "video_publishers": 8, "duration_sec": 120,
      "cpu_peak_pct": 0, "out_mbps_peak": 0, "freeze_rate_pct": 0,
      "first_frame_ms_p50": 0, "first_frame_ms_p95": 0, "reconnects": 0,
      "verdict": "PASS|FAIL" }
  ],
  "nat": [
    { "network": "office|home|lte|tv", "join_ms": 0, "candidate_type": "relay|srflx|host" }
  ],
  "conclusion": "какой максимум с видео подтверждён; нужен ли второй узел"
}
```

## Решение по второму узлу

Второй медиа-узел нужен, если хотя бы одно:

- `cpu_peak_pct > 75` при 12 участниках с видео;
- `out_mbps_peak` упирается в канал провайдера;
- `freeze_rate_pct > 3` на 12 участниках;
- продукт требует 40 участников **с видео** одновременно.

До этого момента волна 2 не начинается: обещать 40 с видео без замера — это ложь клиенту.

## SLO (черновик, уточняется после первого прогона)

| Метрика | Цель |
|---------|------|
| Успешный вход в комнату | ≥ 99% |
| Время до первого кадра (p95) | ≤ 2500 мс |
| Freeze rate | ≤ 2% |
| Reconnect success | ≥ 98% |
| Потеря записи (egress failed) | ≤ 0.5% |
